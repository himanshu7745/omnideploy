Deploy any project, in any language, with one command.

omnideploy looks at your project, figures out what it is, writes the Dockerfile and platform config it needs, shows you what it’s about to write, and deploys it, to Vercel, Netlify, GitHub Pages, Railway or Render. 

$ npx omnideploy-cli deploy render

Needs Node 20+. Or npm i -g omnideploy-cli and type omnideploy.

      §2
      
Why I wrote it

    

    

      

        Every side project ended the same way: an evening spent on a
        Dockerfile that was almost right, a render.yaml copied from a
        project two years old, and a production env var I forgot until the
        app crashed. None of that is hard. It’s just tedious, and slightly different
        for every language and every host.
      

      

        So omnideploy does the boring part. It reads package.json,
        pom.xml, go.mod or requirements.txt,
        and writes the files a careful person would write: multi-stage Dockerfiles,
        pinned base images, a non-root user, listening on $PORT.
        Then it gets out of the way. The files are yours. Edit them, commit them,
        and it won’t overwrite them unless you pass --force.
      

    

  


  

    

      §3
      
What happens when you run deploy

    

    
    
      
  1. Detect the language, framework, port and build command. Anything in omnideploy.json wins over detection.
    2. 
      
  2. Pick providers: the ones you named, else the ones in omnideploy.json, else it asks.
    3. 
      
  3. Check compatibility before touching anything. Spring Boot on Vercel stops here, with a suggestion.
    4. 
      
  4. Check .env.production. If the app needs a variable that’s missing or empty, it stops and names it.
    5. 
      
  5. Generate missing files, show them, and ask. Existing files are kept.
    6. 
      
  6. Get credentials: environment variable, then saved token, then a prompt.
    7. 
      
  7. Sync git (Render only): create a GitHub repo if there’s no remote, commit, push. Render builds from your repo, so the code has to be there.
    8. 
      
  8. Build static sites locally. Servers are built by the platform.
    9. 
      
  9. Deploy to each provider. If one fails, the rest still run.
    10. 
      
  10. Save the site / project / service IDs to omnideploy.json so the next deploy updates the same app.
    11. 
    

    
Exit code 0 if everything deployed, 1 if anything failed, 130 if you hit Ctrl-C.

  


  

    

      §4
      
Quick start

    


    

      

        
        
        
        
      


      

        
$ cd my-project
$ omnideploy deploy render      # or vercel, netlify, github-pages, railway

        
        
It asks for whatever it needs along the way: a token, permission to write files, a repo name. If your app needs config, put the production values in .env.production first and they’ll be set on the platform for you.

      


      

        
$ omnideploy deploy             # every provider in omnideploy.json

        
        
For Render, it lists your uncommitted changes and offers to commit and push them, so what gets built is what you just wrote.

      


      

        
$ omnideploy init               # detect, pick providers, write files
$ omnideploy login netlify      # or set NETLIFY_AUTH_TOKEN
$ omnideploy doctor             # is everything in place?
$ omnideploy deploy

        
        
doctor checks Node, detection, omnideploy.json, .env.production, git and every provider’s token, and gives a fix for each problem.

      


      

        
- run: npx omnideploy-cli@latest deploy netlify --yes
  env:
    NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}

        
        
In CI (or with --no-interactive) it never prompts. It either proceeds because you passed --yes, or fails with a message telling you what to set. It won’t hang waiting for input.

      

    


    
Handy flags

    

      
--dry-run
Show the files and providers. Write nothing, deploy nothing.

      
--preview
Preview URL on Vercel, draft URL on Netlify. Elsewhere it refuses instead of quietly going to production.

      
--dir public
Deploy a folder as a static site, whatever the project is.

      
--force
Regenerate deployment files even if they exist.

      
-C <dir>
Run as if you’d cd’d there.

      §7
      
Secrets stay secret

    

    

      

        Production config lives in one file, .env.production. omnideploy
        works out which variables the app needs (from .env.example, or
        ${VAR} placeholders in Spring config) and stops if one is
        missing. Then it sets them on the platform. Values are never printed,
        and tokens are scrubbed from any git or CLI output it shows you.
      

      

        Before it commits anything, it checks for files that look like secrets
        (.env, private keys, credential JSON) and for tokens pasted into
        source. It won’t upload or push them.
      

    

  


  

    

      §8
      
Things it won’t do (yet)

    

    
    
      
  • Run a server on Vercel, Netlify or GitHub Pages. They host static sites (and, on Vercel, SSR frameworks). It’ll tell you and point you to Railway or Render.
    • 
      
  • omnideploy status for Railway. Check the Railway dashboard instead.
    • 
      
  • Railway deploys need the Railway CLI installed. omnideploy drives it rather than reimplementing it.
    • 
      
  • Provision your database. Point DATABASE_URL at one you already have.
    • 
      
  • Make GitHub Pages work on a private repo without a paid plan. That one’s GitHub’s rule.
    •
